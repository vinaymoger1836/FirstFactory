**arm64 finding, fixed:** Redis 7.4 refused to start on arm64 ("kernel has a bug … ARM64-COW-BUG"). The bug only affects fork-based background saves. Our Redis has persistence disabled (queue state is in Postgres), so it never forks for a save. The compose file passes `--ignore-warnings ARM64-COW-BUG` with that reasoning in a comment. The self-test is known to misfire under emulation; on the Ampere VM the flag is harmless either way.

## 4. Problems found and fixed during the phase

1. **Leaked advisory lock deadlocked the cad-worker.** My first `ensure_schema` took a session-level `pg_advisory_lock` and released it through procrastinate's connection pool. The unlock could run on a different connection (Postgres: "you don't own a lock"), so the lock leaked. The next worker to start blocked on it silently forever. Fixed: one dedicated connection with `pg_advisory_xact_lock`, released by COMMIT. Verified from clean volumes with both workers racing to create the schema.
2. **False-positive readiness.** A recreated worker could look ready because the previous container's Redis heartbeat (60 s TTL) was still fresh. Fixed: each worker image has a Docker HEALTHCHECK on a local heartbeat file (per container, never stale), `make e2e` uses `up --wait`, and heartbeats carry host and PID.
3. **Postgres backend crash (not reproduced).** In one early run, a Postgres backend exited with code 2 and the postmaster reset all connections ("in recovery mode" for about 40 s). This happened while the leaked lock above was in play, and with an arm64 QEMU build loading the host. It did not recur in later runs. Mitigation: workers wait for the DB with backoff and exit hard on fatal errors instead of hanging, so Docker restarts them. **Watch item for P2:** enable `log_connections` and set `application_name` per service if it recurs.
4. **The H1 focus ring showed on first load** (React StrictMode runs effects twice, defeating the "skip first render" guard). Fixed by comparing pathnames. Programmatic focus targets have no ring.
5. **Header overflowed at 390 px.** Fixed: below 480 px the brand text is hidden (the link keeps its accessible name) and gaps are tighter.
6. **`ruff format .` rewrote Python code blocks inside `docs/04`.** Reverted from git (the doc had no other changes) and excluded `docs/` and `*.md` from ruff.

### d. SysML v2: own serializer vs sysml2kit, checked by sysmlpy

Both writers produced the docs/04 §6 example, and both outputs were parsed with sysmlpy 0.98.0 (`loads`) and analysed (`analyze`). Negative controls proved the checks work: broken syntax gives `SysMLSyntaxError`, and unknown types give 2 × `UNDEFINED_SYMBOL` errors.

| | Own serializer (≈150 lines, `spikes/sysml/own_serializer.py`) | sysml2kit 0.4.0 (pre-alpha) |
|---|---|---|
| Parses with sysmlpy | yes | yes |
| `analyze` errors / warnings | 0 / 1 | 0 / 0 (it wrote less) |
| Covers the docs/04 §6 example | **all of it**: `part def` with `:>`, `action def`, routing `action` with `then` succession, `allocate`, `requirement def` with a typed, valued attribute | **no specialisation (`:>`), no action defs, no successions** (routing can't be expressed), `allocate` only between parts, attributes without types |
| Deterministic output | yes (byte-identical reruns) | yes |

**Recommendation: keep our own serializer (ADR-002 unchanged)** and use sysmlpy (pinned exactly) as the validator in P8. sysml2kit's profile has no behaviour (actions or successions), which is the core of our routing mapping.

Findings for P8:
- sysmlpy's bundled library has **no `SI` package** (`import SI::*` → `UNRESOLVED_IMPORT`). The serializer therefore omits `SI::*`, which differs from the docs/04 §6 example text. Unit literals like `[mm]` will need SI: decide in P8 whether to bundle the OMG library files for `analyze`.
- sysmlpy also warns `IMPLICIT_LIBRARY_IMPORT` for `ElectricChargeValue` even with an explicit `ISQ::ElectricChargeValue` import. This looks like a sysmlpy name-resolution gap, not a model error. Treat warnings as non-fatal.
- A cold parse takes about 3.5–4 s (its ANTLR DFA cache fails to save: `RecursionError`), then about 20 ms. That is fine for an export step. Don't call it per request.
- sysmlpy publishes several releases a day and has no licence metadata on PyPI (README says MIT). Pin it exactly and confirm the licence before P8.

### e. Worker queue: arq + Redis vs procrastinate (Postgres)

Bench in `spikes/queue` (Docker; one worker at concurrency 1 each; same no-op and 15 s sleeper tasks; the worker is SIGKILLed 2 s into the sleeper and a fresh one started).

| | arq 0.28.0 (`poll_delay` 0.5 s default) | arq (`poll_delay` 0.05 s) | procrastinate 3.10.0 |
|---|---|---|---|
| Enqueue → start, 200 jobs at 50/s, p50 / p95 | 48 s / 91 s (backlog: about 2 jobs/s) | 2.9 s / 5.6 s | **6.4 ms / 25 ms** |
| 200-job burst drain | 100 s | 10 s | **1.3 s** |
| Recovery after SIGKILL mid-job | 38 s (`job_timeout` 30 s + 10 s) | 38 s | **30.5 s** (heartbeat-based, independent of job length) |
| Idle worker RSS | 46 MB | 46 MB | 48 MB |

**Recommendation: procrastinate (ADR-019, Proposed).** The decisive points are not raw speed:
- arq recovery time grows with `job_timeout`, so a 10-minute simulation timeout means up to 10 minutes before a crashed job reruns;
- arq is in maintenance-only mode and pins `redis<6`;
- Postgres is already the system of record.

procrastinate does not retry stalled jobs on its own, so the worker runs a one-minute sweep (`retry_stalled_jobs`).
